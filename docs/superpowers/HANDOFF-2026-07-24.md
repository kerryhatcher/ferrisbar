## The problem being fixed right now

Branch protection (Project 2) requires 7 CI checks before a normal merge.
But release-please opens its PR using the default `GITHUB_TOKEN`, and
GitHub's docs are explicit: **events from `GITHUB_TOKEN` — including PR
creation, not just pushes — never trigger other workflow runs, regardless
of the token's permission level.** So `ci.yml`'s `pull_request:` trigger
never fires on PR #1, no checks ever appear on it, and a plain
`gh pr merge` is blocked ("the base branch policy prohibits the merge").

Investigated alternatives with the user:
- rustywx doesn't hit this because it has **no branch protection at all**
  (`gh api repos/kerryhatcher/rustywx/branches/main/protection` → 404).
  Its pattern solves the *tag-push* PAT problem, not this *PR-open*
  problem — they're separate GitHub restrictions that happen to have the
  same root cause.
- GitHub Rulesets' per-actor bypass (e.g. "let this specific bot skip
  checks") is an org/enterprise feature — `kerryhatcher` is a personal
  account, so that route doesn't exist here.
- User explicitly rejected the `--admin` bypass-merge option and a plain
  PAT, and asked instead for a **GitHub App** (the officially-recommended
  alternative to a PAT for exactly this "bot needs its PR to trigger real
  CI" scenario — App installation tokens aren't subject to the
  GITHUB_TOKEN restriction).
